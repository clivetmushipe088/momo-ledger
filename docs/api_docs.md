# MoMo SMS Ledger: API Documentation

Base URL: `http://localhost:8000`. The interactive version of this page, generated by FastAPI, is at <http://localhost:8000/docs>.

---

## Authentication

Accounts are created with `POST /auth/register`. `POST /auth/login` checks the password against its bcrypt hash and sets a `session` cookie:

- 32 random bytes (`secrets.token_urlsafe`), stored in the `sessions` table
- `HttpOnly` (JavaScript can't read it) and `SameSite=Lax` (not sent with requests started by other websites)
- valid for one day

Every route except register and login needs that cookie, otherwise it answers `401 {"detail": "Please log in first."}`. With curl, save the cookie with `-c cookies.txt` on login and send it with `-b cookies.txt` afterwards.

---

## Endpoints

| Method | Path | What it does | Success |
|--------|------|--------------|---------|
| POST | `/auth/register` | Create an account | 201 |
| POST | `/auth/login` | Log in (sets the `session` cookie) | 200 |
| POST | `/auth/logout` | Log out | 200 |
| GET | `/auth/me` | Who is logged in | 200 |
| POST | `/upload` | Import an XML backup (form field `file`) | 200 |
| GET | `/unmatched` | MoMo messages no rule understood | 200 |
| GET | `/transactions` | List, with `type`, `status`, `min_amount`, `max_amount`, `page`, `limit` | 200 |
| POST | `/transactions` | Add one by hand | 201 |
| GET | `/transactions/{id}` | Read one | 200 |
| PUT | `/transactions/{id}` | Change one (send only the fields to change) | 200 |
| DELETE | `/transactions/{id}` | Delete one | 200 |
| GET | `/reports/monthly-flow` | Money in and out per month | 200 |
| GET | `/reports/merchants` | Top 10 merchants by money spent | 200 |

### Transaction fields

| Field | Type | Rules |
|---|---|---|
| `transaction_type` | string | `incoming_money`, `payment`, `transfer` or `airtime` |
| `amount` | integer | whole RWF, greater than 0 |
| `party` | string | the other person or merchant, up to 100 characters |
| `date` | string | `YYYY-MM-DD HH:MM:SS` or ISO 8601 |
| `status` | string | `completed` (default), `pending`, `failed` or `reversed` |

`id`, `sms_ref` and `raw_sms` are set by the server.

## Request and response examples

All responses below are real output from the app after uploading `data/modified_sms_v2.xml`.

### Register and log in

```bash
curl -H "Content-Type: application/json" -d '{"username":"clive","password":"password123"}' \
  http://localhost:8000/auth/register
# {"message":"Account created. You can log in now."}

curl -c cookies.txt -H "Content-Type: application/json" -d '{"username":"clive","password":"password123"}' \
  http://localhost:8000/auth/login
# {"username":"clive"}
```

### Upload a backup

```bash
curl -b cookies.txt -F file=@data/modified_sms_v2.xml http://localhost:8000/upload
# {"imported":25,"duplicates":0,"unmatched":0,"ignored":0}
```

Uploading the same file again gives `"imported":0,"duplicates":25`.

### Create

```bash
curl -b cookies.txt -H "Content-Type: application/json" \
  -d '{"transaction_type":"transfer","amount":5000,"party":"Bob","date":"2024-02-01 10:00:00"}' \
  http://localhost:8000/transactions
```

```json
{"id": 26, "sms_ref": null, "transaction_type": "transfer", "amount": 5000, "party": "Bob",
 "date": "2024-02-01 10:00:00", "status": "completed", "raw_sms": null}
```

### Update

```bash
curl -b cookies.txt -X PUT -H "Content-Type: application/json" \
  -d '{"status":"reversed","amount":5500}' http://localhost:8000/transactions/1
```

```json
{"id": 1, "sms_ref": "TXN001", "transaction_type": "incoming_money", "amount": 5500, "party": "Alice",
 "date": "2024-01-03 08:12:00", "status": "reversed", "raw_sms": "..."}
```

### Delete

```bash
curl -b cookies.txt -X DELETE http://localhost:8000/transactions/1
```

Returns `200`. A second delete of the same id returns `404`.

### Errors

| Status | When |
|---|---|
| 400 | Username already taken, the upload isn't valid XML, or the database rejected the data |
| 401 | Not logged in, session expired, or wrong username or password |
| 404 | Transaction not found (or not yours) |
| 413 | Upload bigger than 5 MB |
| 422 | Request body failed validation, e.g. a negative amount or a bad date; the body says which field and why |

```bash
curl -b cookies.txt -H "Content-Type: application/json" \
  -d '{"transaction_type":"transfer","amount":-500,"party":"Bob","date":"not a date"}' \
  http://localhost:8000/transactions
# 422, with one entry per bad field
```

## How the parsing works

A real phone backup only has the message text and a date, so `app/parsing.py` only reads those two, even though `modified_sms_v2.xml` also has ready-made fields.

1. A message without `RWF` in it isn't a MoMo message (chats, OTP codes) and is skipped.
2. Each rule is a regular expression for one message format, for example:
   `You have received 5000 RWF from Alice (0781234567). TxnId: TXN001`
   gives type `incoming_money`, amount `5000`, party `Alice`, reference `TXN001`.
3. Dates are either milliseconds since 1970 (what Android backup apps save) or `YYYY-MM-DD HH:MM:SS`. They're stored as Kigali time.
4. A MoMo message that no rule matches goes into the `unmatched_sms` table and shows up in the dashboard.

The original text is saved with every record (`raw_sms`), so after adding or fixing a rule the messages can be parsed again. To support a new format, add a line to `RULES` and a test to `tests/test_parsing.py`.

## The app's database (SQLite)

`app/schema.sql` creates four tables and two views:

- `users`: username and bcrypt password hash
- `sessions`: one row per logged-in browser, valid for one day
- `transactions`: one row per transaction, linked to its user
- `unmatched_sms`: MoMo messages the rules couldn't read
- `v_monthly_flow` and `v_merchant_spend`: the sums behind the two charts

Some decisions worth knowing:

- **Amounts are whole numbers (`INTEGER`).** RWF has no cents, and storing money as a float can give rounding errors.
- **`UNIQUE (user_id, sms_ref)`** stops the same SMS being imported twice. Hand-added transactions have no `sms_ref`, and SQLite allows any number of NULLs, so they're unaffected.
- **Two layers of checks.** Pydantic rejects bad input first. The `CHECK` constraints in the database (positive amount, known type and status, date format) are the backup if something slips through.
- **Every query filters by `user_id`**, so one user can never read or change another user's data.

---

## Security

- Passwords are stored only as bcrypt hashes.
- Every value goes into SQL as a bound parameter (`?`), so request data can't change a query.
- Every transaction query includes `AND user_id = ?`, so users only ever see their own rows.
- Pydantic validates every request body before it reaches the database.

## Data

- `data/modified_sms_v2.xml`: 25 MoMo SMS messages.

## Not done yet

- **HTTPS.** The cookie is set with `secure=False` so it works on `localhost`. On a real server it should be `True`, behind HTTPS.
- **Login rate limiting.** Nothing stops someone trying many passwords quickly.
- **More message formats.** Only four are understood. Real MTN messages include withdrawals, bank transfers and more; for now they appear under "couldn't be read".
- **Messages without a transaction id** can't be checked for duplicates.
- **Very large backups.** The whole file is read into memory (limit 5 MB). `ElementTree.iterparse` would fix this.
- **Docker.** No container setup yet.
